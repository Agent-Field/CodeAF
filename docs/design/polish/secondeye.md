# Second-eye findings

1. **`cmd/aforge/vocabulary_test.go:68` — the test named “old spelling still works” never checks that the old spelling works (high).** `captureNotice` deliberately discards the command's returned error, and every table row asserts only that a one-line rename notice contains the new spelling and “one more release.” An alias can print that notice and then fail as an unknown flag, reject the old value, or route to the wrong command, and this test remains green. That matters most to scripts using the compatibility window: the UI tells them the spelling is supported while the invocation is already broken. The smallest fix is to have each case return the door's error plus one observable semantic result, and assert at minimum that parsing succeeds (then assert the old flag changes the same value as the new flag; for command renames, drive a cheap pre-provider seam that proves the intended door was entered). Putting the entire old implementation back would generally make this test red because the notice disappears, but putting back the actual defect named in the title—an old spelling that no longer works while leaving the new notice in place—does not.

2. **`cmd/aforge/run.go:49` — an existing file shadows a saved program with the same name (high).** The new contract says `aforge run <program>`, but compatibility routing treats *any* regular file in the first positional slot as an old `aforge run <plan.json>` invocation. Thus `aforge run formatter --input input.json` runs the file `./formatter` as a static plan whenever that file happens to exist, instead of running the registered program named `formatter`. The result depends on the caller's current directory and can execute an entirely different workflow. No test covers the collision; the current rename test only supplies an unambiguous plan file. The smallest fix is an explicit compatibility discriminator—prefer the program registry when `--input` is present or the name resolves as a program, and only fall back to the legacy plan route otherwise (or require a `.json` plan that successfully decodes before routing).

3. **`cmd/aforge/exec.go:354` — a limited/partial run can publish both an answer and a non-empty `error`, contradicting the new envelope contract (high).** `execStop` intentionally preserves `budget`, `turn-cap`, or `deadline` when `linear.Run` returns both an outcome and an error, but `buildExecEnvelope` independently copies every `runErr` into `Error`. The contract at `cmd/aforge/envelope.go:249` says `error` is empty whenever an answer was produced and means the run could not be run at all. A caller following that contract can therefore discard useful partial output or classify a limit stop as a startup failure. The tests cover an `error` stop and limit stops separately, but not a limit outcome with partial text plus `runErr`. The smallest fix is to derive `stop := execStop(...)` once and populate `Error` only when `stop == stopError`; if the limit's diagnostic must remain machine-readable, give it a separately defined field whose meaning includes partial runs.

4. **`internal/tui3/settings.go:2351` — tab geometry counts bytes where the terminal needs display cells (low, currently latent).** `tabChipCols` uses `len(title)`, while drawing and hit-testing around it use `ansi.StringWidth`. All current tab titles appear ASCII, so this is not presently visible; it becomes wrong as soon as a translated/CJK title or combining mark is introduced. Then `tabWindow` can hide too many/few tabs, and the spans used for pointer clicks disagree with the painted cells. The current tests also convert the rendered bar to `[]rune` and slice it with cell offsets, so they would not settle the combining-mark case. The smallest fix is `ansi.StringWidth(title) + tabPadCols`, plus a test using a double-width rune and a combining sequence and inspecting spans by display cells rather than rune indices.

5. **`cmd/aforge/usage.go:137` — per-command help wraps by bytes, not terminal cells (low).** `wrapAt` measures `len(lines[last])` and `len(word)` although its stated purpose is fitting an eighty-column terminal. Provider-authored or future localized help containing CJK can overrun; combining marks can wrap early. This is a confirmed arithmetic mismatch but a currently latent UX defect because the checked-in English help is mostly ASCII. The smallest fix is to use `ansi.StringWidth` (or the repository's shared display-width wrapper) and add wide/combining-word cases.
