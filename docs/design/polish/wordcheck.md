2. **SENTENCE NOT TRUE OF THE CODE — exit 1 is described as a run that never started, but `exec` runtime errors also land there.** `cmd/aforge/envelope.go:120-122` publishes `"could not be run at all"` / `"it could not be run at all — no key, bad arguments, the store would not open"`; the same claim reaches the manual at `internal/manual/chat/running-from-the-terminal.md:42` and its `error` field description at `internal/manual/chat/running-from-the-terminal.md:92`. In the surrounding code, `cmd/aforge/exec.go:288-294` preserves `exec.StopError`, and `cmd/aforge/exec.go:307` sends it through `exitFor`, so an error returned after the executor produced an outcome is also exit 1. That can make a script discard a run that did start, may have spent money, and may have partial evidence. **Judged, not counted:** I am confident about the control flow; I am unsure whether every current producer of `exec.StopError` can carry partial answer text, but the state is explicitly an executor outcome rather than a pre-run refusal. **Fix:** map an `exec.StopError` outcome to the “ran and did not finish” rung, reserving `stopError`/exit 1 for `outcome == nil`, or broaden the published sentence so it no longer claims nothing ran.
