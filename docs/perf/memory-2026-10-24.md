# Desktop engine resident memory, 2026-10-24

`codeaf app` is the desktop app's engine. On a large home it sat near 1 GB
resident at idle. This records how that was measured, what held the memory, and
what changed.

## Workload

A private copy of a real desktop home (cloned with `cp -c`, never the original):
2.5 GB on disk, 20 open crews, 211 agents, 250 journals (the largest 98 MB, ten
over 10 MB, 460 MB in all), 2,638 tasks (one agent has 909, with an 1.1 MB plan
store). Machine: macOS, darwin/arm64, 28 cores.

## Method

1. Build `GOOS=darwin GOARCH=arm64 CGO_ENABLED=0 go build ./cmd/codeaf` and run
   `env -u GOGC -u GOMEMLIMIT codeaf app --home <copy>` as the desktop app does,
   with stdin held open. Both collector environment overrides must be absent.
   `CODEAF_DIAGNOSTIC_PROFILE_DIR` and `CODEAF_DIAGNOSTIC_PROFILE_HEAP=1` write a
   heap profile at 60 s (`internal/diagprofile`).
2. With no client attached the engine idles at about 180 MB. The rest comes from
   what the desktop asks for, so a small driver speaks the JSON-lines protocol the
   way the all-crews task view does: `crews.list`, `agents.list`, then `tasks.list`
   and `processes.list` for every agent, then `agents.entries` for one chat, then a
   second `tasks.list` pass.
3. Sample at 1, 3 and 10 minutes: `ps` RSS, `vmmap --summary` physical footprint
   and CPU time. `go tool pprof -sample_index=inuse_space` and `alloc_space` on
   the heap profile.
4. Check equivalence: the ids and states of all 2,638 tasks and 2,094 processes
   were identical before and after.

macOS keeps pages the Go runtime frees (`MADV_FREE_REUSABLE`) in a process's
resident size until it needs them, so `ps` RSS reports the peak of a burst. The
physical footprint (Activity Monitor's Memory column) reports what is held. Both
are given.

## What held the memory (baseline, heap at 60 s: 383 MB in use)

| Retainer | In use |
| --- | --- |
| Journal replay of held conversations (`newAgent` → `readJournal`) | 275 MB |
| Journal records for appended jobs/steps (`RecordCache`, up to 256 MiB, 32 records, never expired) | 50 MB |
| everything else | about 60 MB |

The replay came from `findCrewOwner`: every read of a member of an open crew
(`tasks.list`, `asks.list`, `processes.list`) opened its conversation and kept it
held for as long as the crew was open. With `GOGC` unset, the baseline app uses Go’s default collector percent,
100, which targets about twice the live heap. `codeaf app` does not call
`tuneForTheSurface`; the terminal’s initial setting of 400 does not apply. The wave-1 lazy opening (`4e6b49999`) had measured
230 MB; the read paths had since drifted back to opening everything.

Allocation, not retention, drove the peaks: 17.8 GB were allocated in 60 s, 38%
by `plandb` reloading the whole plan on every read (once per run row), 15% by
decoding the project task index once per conversation, and a quadratic copy of
run rows.

## Changes

| Change | Gate |
| --- | --- |
| `plandb.Store` reloads only when SQLite `data_version` or the db/log stamp moved | 200 reads: 153 MB → under 3 MB |
| `AppTasks` opens the plan once for all run rows; `markPlanInterrupted` stops copying rows | 150 rows: 235 MB → under 16 MB |
| Project task index decoded once per file stamp, shared | 40 reads: 180 MB → under 64 MB |
| `RecordCache` drops records unread for 30 s, keeps 8 | `TestAKeptRecordNobodyAsksForIsDroppedWhenItIdles` |
| Members at rest are read, not held; their task list is built in one short hold and remembered by file stamp, in memory (24 MiB LRU) and under `<home>/cache/app-tasks` | `TestAppReadingAnIdleCrewMemberDoesNotKeepItsConversation`, `TestAppReadsARestingMembersTasksFromTheCacheAfterARelaunch` |
| Idle crew members are let go after the 10-minute idle time | `TestAppLetsAnIdleCrewMemberGoAfterTheIdleTime` |
| Collector percent follows the live heap (32 MiB of headroom); unused held heap is returned | `TestHeapGovernorKeepsTheHeadroomNearlyConstant`, `TestHeapTrimmerReturnsOnlyAnExcessAndOnlyOncePerCooldown` |

## Result

Engine process, same copy and driver. RSS is `ps`, footprint is `vmmap`.

| | 1 min | 3 min | 10 min | footprint at 10 min | peak footprint | CPU at 10 min |
| --- | --- | --- | --- | --- | --- | --- |
| Before | 986 MB | 987 MB | 989 MB | 843 MB | 941 MB | 75 s |
| After, first launch (no cache) | 413 MB | 415 MB | 417 MB | 206 MB | 359 MB | 39 s |
| After, relaunch (cache present) | 242 MB | 243 MB | 245 MB | 170 MB | 195 MB | 20 s |

Heap in use at 60 s: 383 MB before, 89 MB after (relaunch). No growth from 1 to
10 minutes in any run (before +3 MB, after +4 MB and +3 MB).

For the reproduction command above, `GOGC` and `GOMEMLIMIT` are unset. The
runtime starts at collector percent 100 and the default unlimited soft memory
limit (`math.MaxInt64` bytes). The app installs no half-RAM limit. After this
change, `startHeapTrimmer` adjusts the collector percent to
`clamp(32 MiB * 100 / live heap, 10, 400)` on its first step, after collections
and on its five-second checks, with a 20% change threshold. An explicit
`GOGC=400` disables that adjustment and is a different experiment. The trimmer
also returns unused heap when its excess exceeds both 48 MiB and half the live
heap, at most once per minute.

The table records the original measurements, not a rerun of the review fixes;
the original per-run environment and runtime settings were not captured.
Reproduce with the explicit unset environment above before attributing the
numbers to a particular collector configuration. The 245 MB figure meets the
250 MB target on a relaunch. The first launch
does not: building each member's task list once replays its journal, and the
largest journals (98 MB, 31 MB) drive a transient peak of 359 MB footprint.

## Cache bounds and validity

The 24 MiB task-list budget estimates retained Go memory: task structs, slice
capacity, pointed-to values, string bytes, stamps, entry and LRU storage, plus
128 bytes per entry for map/allocator overhead. Shared references are counted
again conservatively; process-owned time-zone data is excluded. This is an
estimate of retained cache data, not a process RSS ceiling.

Both memory and disk task-list reads use the same two read slots. Disk files
are stat'ed before decoding and capped at 24 MiB; an entry the memory budget
rejects is never written. Invalid disk entries are removed. Files must match
replacement-sensitive stamps from before opening through the completed read
and release. Files modified or changed within two seconds are read afresh. Task/process
child files and both a cell’s truth folder and session root are stamped too.
Flat legacy journals with external dependencies are read without caching. An unstable read is returned but never cached.
Reader references keep the owner alive; idle release rechecks current tasks,
quick tasks and jobs under the same gate that admits work.

## Left

- First launch peak: a read-only way to build the task list without replaying the
  journal (a task-only open) would remove it; `Open` also writes recovery state,
  so it needs care.
- A held conversation costs about its journal size. Journals above a compaction
  keep every display row in memory.
- `<home>/cache/app-tasks` files for deleted agents are not pruned; `codeaf cache
  clean` removes them.
- No protocol field changed and none needs paging by the UI. `tasks.list` of one
  agent can be 3 MB; paging it would shrink the largest transient further.
