# Footprint comparison, 2026-09-17

One Linux machine (aarch64, 20 cores, 119 GB RAM), one repository (a CodeAF checkout, 3,249
Go files), one session. Every CLI on its own authenticated profile. Method and limits:
[how the footprint numbers are measured](README.md).

CodeAF is at `825ef2c4` plus the package-init changes that landed beside this file. Startup
figures for the others predate nothing; `--version` for CodeAF is measured after those changes.

## The six others

They are not named. What matters to the numbers is how each one is delivered, so that is what
is given, and the labels are stable across every table below.

| | how it is delivered |
| --- | --- |
| **CodeAF** | one static binary, Go |
| **B** | one static binary |
| **C** | versioned install directory with a bundled runtime |
| **D** | versioned install directory with a bundled runtime and a bundled search tool |
| **E** | package tree on a system interpreter |
| **F** | package tree on a system interpreter |
| **G** | package tree on an alternative interpreter |

## Startup

Cold start is best-of-20 for `--version`. First frame is time to the first non-blank character
painted in a 160x48 pane, on an authenticated profile, in the repository, with any folder-trust
dialog cleared first.

| | cold start | first frame |
| --- | --- | --- |
| B | **5-7 ms** | **131 ms** |
| C | 8-11 ms | 572 ms |
| **CodeAF** | **12.5 ms** | **208 ms** |
| D | 306-479 ms | 1,298 ms |
| F | 314-352 ms | 2,420 ms |
| E | 330-360 ms | 398 ms |
| G | 337-387 ms | 400 ms |

**B is faster than CodeAF on both**, by about 2x on cold start and 1.6x to first frame. Both are
single static binaries, so the gap is not delivery: it is package init, of which about 7.3 ms is
one dependency's lexer registry parsing its embedded definitions before `main`.

The four interpreter-hosted CLIs never get under 300 ms, because the runtime boots first.

## Startup work

`strace -f -e trace=openat,connect,execve` over `<cli> --version`, the same command for every
CLI, invoked directly with no wrapper process.

| | `openat` | succeeded | `connect` | `execve` |
| --- | --- | --- | --- | --- |
| **CodeAF** | **15** | 13 | **0** | **1** |
| B | 16 | 14 | 0 | 1 |
| C | 30 | 27 | 0 | 1 |
| F | 45 | 39 | 0 | 1 |
| G | 86 | 79 | 0 | 2 |
| D | 363 | 355 | 18 | 18 |
| E | 1,581 | 1,481 | 0 | 7 |

15 against B's 16 is a tie in everything but arithmetic. Five of the seven open no network
connection to print a version; D opens 18, nine of them to the network, and runs 18 processes.

## Where this table has been wrong before

An earlier version of the startup-work table gave CodeAF 54 opens and 3 execs, and others up to
6,024 opens and 252 network connections. Those numbers are withdrawn: the script that produced
them traced CodeAF as a full interactive boot while tracing the others as `--version`, and
wrapped every CLI in `env`, which added a phantom `execve` to every row. The error ran against
CodeAF and the correction favours it, which is the reason to record the correction rather than
quietly replace the figures.
