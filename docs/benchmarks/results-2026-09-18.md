This file records one session's memory measurements and nothing else. It does not replace
`results-2026-09-17.md`, which stays as that day's record. It supersedes that file's idle
memory column, for the reason given under "Why the old column is retired".

Every CLI ran on its own authenticated profile with folder-trust dialogs already cleared.
The gate for a measurement was memory pressure, not CPU load: `some avg10` at or below 1.0
percent and at least 8 GB `MemAvailable`. RSS, PSS, peak RSS, threads and file descriptors
are properties of a process rather than rates, so a busy CPU does not move them. Reclaim
does, which is what the pressure gate watches. Pressure read 0.00 before and after all
seven windows and no page was swapped out during any of them.

## Memory at rest

PSS counts a shared page once and is the figure to compare when a CLI runs more than one
process. `procs` is how many processes of the CLI's own tree were alive at the last sample.
`seen` is how many distinct processes the tree held at any sample, so a CLI that starts
helpers and reaps them is visible rather than hidden behind a single count.

## What this figure is not stable to

CodeAF measured 80.5, 82.6, 83.5, 81.0 and 76.1 MB PSS across five passes on this machine
today, two builds and one script revision. That is a spread of about 10 percent on an
unchanged program, so quote about 80 MB rather than any single run's figure, and do not
read a change of a few MB between builds as a result.

## Why the old column is retired rather than patched

`measure-cli.sh` walked `/proc/<pid>/task/*/children` to find a CLI's processes, and the
walk never descended. Linux `children` files carry no trailing newline, so the shell's
`read` filled its array and then reported end of file, and the code treated that report as
a failure and discarded the children it had just read. Every CLI was therefore measured as
a single process whatever it actually ran. `a1f1e805` fixes it and
`process-tree-recovery-2026-09-18.md` records the timeline and the test that proves it.

That defect moved every row, not only CodeAF's, and in both directions. Against the
2026-09-17 table: CodeAF rises from 66 to about 80 MB, because its engine daemon was never
counted; claude falls from 305 to 205, cursor-agent from 413 to 194, opencode from 708 to
678, omp from 388 to 324 and pi from 156 to 126. A table wrong in both directions cannot be
corrected row by row, so the whole column is measured again here instead.

The correction runs against CodeAF. The honest figure is larger than the one published, and
it is published for that reason.

## The timing columns are not in this table

First frame was recorded this session but is not comparable and is not reproduced here. The
machine's one-minute load ran from 4.7 to 23.1 across the seven windows, and four CLIs were
measured while it was above 13. A millisecond figure taken under that contention measures
the contention. The memory figures are unaffected, which is the whole reason the gate reads
pressure and swap rather than load.

For the record and not for comparison, CodeAF's first frame measured 340 ms here and 344 ms
on a separate probe of the same build, against 354 ms on the previous build `4f002ca2`. The
lazy lexer change did not move it.
