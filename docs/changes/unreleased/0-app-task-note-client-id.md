---
kind: added
title: codeaf app keeps a task note's client id on the page and the event
pr: 0
surface: [engine]
invalidates:
  - "Was true: `tasks.note` took a `client_id` that only the returned entry echoed; `tasks.get` notes had no `client_id` and were named `<task>.n<position>`, and `note.changed` named the process-local `tnN`, so a surface could pair its sent note with the page only by words. Is true now: for a graph task the engine stores the opaque, bounded (`MaxClientIDBytes`, 256 bytes) `client_id` with the note in its persisted record, so it survives a restart, and `tasks.get` notes and `note.changed` carry it. Keyed run-row and direct plan-note producers also store the key in the same SQLite transaction as the note; supported run-row pages echo that persisted key. Absent still means unknown: unkeyed plan-store notes, the task's own lines, unsupported page views and records from before this change carry none, and nothing is matched by text or stamped by position. `tnN` ids remain process-local."
  - "Was true: a graph task note's `client_id` was written to the app's own sidecar in a second write after the note was delivered, so a delivered note could come back as an error, and a running quick task's note went through an unkeyed fallback. Is true now: the key is written onto the task's direction in the same checkpoint write that admits the words, before any worker is handed them; a disk that refuses that write refuses the note with nothing delivered. A running quick task takes a keyed `note` through `AppTaskAction` too, and a settled one is still refused. Two notes under one key are two notes: the key is never a retry identity. A `brief` whose page brief cannot be kept after delivery answers `ErrBriefNotKept`, which is not a refusal. Sidecar keys written by earlier builds still read back where the direction has none."
  - "Was true: a note sent through the typed receipt could be reported `refused` when its plan-store commit failed, or when the engine's door panicked after the words were written. Is true now: a failed SQLite commit (`plandb.ErrCommitUncertain`) on any plan-store road, a plan task's `brief` included, and a panic inside the engine's receipt door are both `unknown`, so the app keeps the words under their key and never sends them again; only failures raised before the commit or before the door are `refused`. A call that asks for the receipt from an engine without the receipt door is refused before any plain mutation is called; the app conservatively answers `uncertain`, because an untyped error never establishes refusal. A graph `note` no longer advances a task's `version`, because the app sidecar write is gone: an `expect.version` taken before a note still matches after it, and a client must not key a page refetch on the version changing for a note; it refetches by the note's `client_id`."
  - "Was true: `tasks.brief` went through the engine's plain task door, and every app conversation reaches its engine over the remote socket, where that door's error is bare text with no sentinel left in it. A brief delivered with its page brief unkept (`ErrBriefNotKept`), a plan task's amendment whose commit failed (`plandb.ErrCommitUncertain`) and a brief whose reply never came all answered an ordinary error code such as `engine`, which invited a second send that would land the brief twice. Is true now: `tasks.brief` is sent through the typed receipt door that `tasks.note` uses. An unknown outcome, a brief whose page brief was not kept, a lost reply and an engine that cannot type the outcome all answer `uncertain`, and none is sent again by any door; the plain door is never the fallback. A typed refusal keeps its own code, and only a refusal that the task is not listed yet is asked again for a few seconds, because nothing was done. The request and its success answer are unchanged. Against an engine from before the receipt, every brief answers `uncertain`, a brief that landed included, because that engine cannot say. The other `tasks` verbs still use the plain door: across the socket their errors stay text, so `appTaskError`'s sentinel mapping applies to them only in process."
  - "Was true: an answered error on the receipt call was read as refused when the current welcome advertised receipts. Is true now: every untyped error is unknown, regardless of the welcome; only an explicit typed refused receipt establishes refusal, and nothing is automatically sent again."
