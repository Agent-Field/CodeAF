title: A factory job runs one default recipe however it started, and a step that falls short gets another round
pr: 0
surface: [engine, chat, docs]
invalidates:
  - "Was true: there were two default recipes. A job as it arrived, and every job a person started, ran `factory.DefaultRecipe` (plan asked `read the issue and say how`, test 2 rounds, review 1, everything else 1, security off in the list, nothing fixed); a job a start rule started was re-stamped with `pipeline.Defaults`, which had other asks, no rounds at all, `fixed: [approve, proof]`, and for a pull request `read › review › proof` and for a red main `read › write › test › proof`, with no approve step. Is true now: `factory.DefaultRecipe` is the one definition, built from one table of shipped stages (`factory.ShippedStages`), and `pipeline.Defaults` and the built-in steps are read off it, so `pipeline.Defaults().Recipe()` is the default recipe stage for stage and a job runs the same steps, asks and rounds whoever started it."
  - "Was true: most default steps ran once, so a review that found one problem or a proof with one claim not shown stopped the job at the out-of-rounds question. Is true now: plan, write, read, checks, bisect and fix get 2 rounds; test, review, security and proof get 3. A pipeline file's `max:` still replaces them, and a step of the file's own with no `max:` still runs once."
  - "Was true: the default issue steps were plan › approve › write › test › review › security (off) › proof, a pull request's read › checks › review › security (off) › proof › approve, a red main's bisect › fix › test › proof › approve, and a pull request's review and proof had asks of their own. Is true now: issue plan › approve › write › test › review › proof; pull request read › checks › review › proof › approve; red main bisect › fix › test › proof › approve; one name is one stage, so every kind's review and proof is the same step. approve and proof are fixed in the default recipe too. security is shipped but in no list: the `security` word on a typed job adds it after review, and a markdown line that names a shipped stage with no ask copies it (never its `fixed`)."
  - "Was true: only a round of a stage that runs until clean, green or proven was told what the round before found, and only the first line of its output and its unshown claims, cut at 1,500 characters. Is true now: every round after the first, whatever its until, opens with `round N of <step>. The last round reported:` and the last report line by line (its output, `N findings still open`, each `not shown: <claim> (<evidence>)`), cut at 4,000 characters; a stage judged on what it leaves is told `Fix what it left in the checkout first, run the tests, then <step> again and report only what is still wrong.`, one that runs until done `It did not finish. Carry on from what it left in the checkout, and report done once the ask is carried out.` Each round is still a fresh conversation, and the last round's notes still reach it through the brief's notes."
  - "Was true: nothing said whether `findings` counted what a round found or what it left, so a reviewer that fixed three problems and reported three failed. Is true now: a stage that runs until clean is told `findings counts only what is still wrong once this round's own fixes are in: a problem you found and fixed is not a finding, and review is clean at zero.`, and `stage_result`'s findings field reads `Problems still wrong after your fixes.`"
  - "Was true: `stage_result`'s schema let a claim leave out `evidence`. Is true now: `evidence` is required on every claim, and a stage that runs until proven is told in its brief `every claim needs its evidence, what shows it (the command and its result, the file, the screenshot): a claim with none is not proven.` The words live in the brief, not the tool, which every call pays for. The call is not yet checked against it when it is made."
  - "Was true: `RepairShipDefault` read the old ship default off the current default recipe. Is true now: it compares against the list the floor wrote then, spelled once, so moving the default does not stop old items from being repaired."
---

Not done here: checking a report against its step's rule when `stage_result`
is called (a proof claim with blank evidence, a review reporting done with
findings still open) belongs to the round-lifecycle work that lets a later
report replace an earlier one. A job a person starts on a repository WITH a
pipeline file still runs the stages stamped when it arrived, while a rule's
start re-reads the file; that is unchanged.
