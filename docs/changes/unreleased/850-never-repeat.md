invalidates:
  - "A retry re-sent the bytes encoded once above `provider/retry.go`'s attempt loop, so `provider.order` / `only` / `ignore` were fixed for the whole call and every attempt went to the same machine — 53 % of ten days of multi-attempt chains never left the lane they started on, and three spent sixteen and seventeen consecutive sends on one machine over eleven minutes. The body is now written per attempt, with the machines that refused THIS CALL dropped from it (`refusedHere` → `callKnobs.refused` → `wirePreferences`'s `dropRefusedHere`). `velocity.go`'s own sentence, 'the retries of the call that drew the 429 still wait it out, because their body is already written', is deleted."
  - "The exclusion keys on the machine that ANSWERED, never on the machine we asked for. `provider.order` is advisory once `allow_fallbacks` is true: in the 2026-09-10 22:20 run every attempt asked for DeepInfra and Parasail answered eighteen 429s on one node, so re-ordering excluded nothing. The next body carries `provider.ignore: [the `(via X)` in the refusal]`, and the lane we asked for is left in the order and never struck — it did not answer, so it has said nothing."
  - "`retryElsewhere` and `demandedPoolIsFull` (#835) were two exits answering one question and could disagree — a 429 naming a rescue's machine went back to the race, a 502 naming it did not. They are one door now, `Client.handBack`: a strict pin never hands back, a refused demand goes back at once, an account-wide pacing never does, and everything else goes back when the race can fund an alternative."
  - "`Retry-After` was read from the header only, and the census recorded it on not one row in ten days while every fourth failure was a 429 — this router names its comeback in the refusal envelope. `retryAfterIn` now reads `retry_after` beside the error, on it, and in its metadata, still capped at `maxProviderWait`."
  - "A 429 that named no pool was always an account-wide limit and wrote nothing. Under a demand of exactly one machine it is now filed against that machine, because a demand of one machine IS the whole serving set. With nothing demanded it still writes nothing."
  - "`velocity.go`'s refusal door and its two paces were switched off by configuration — `c.velocity == nil || !c.carriesPreferences() || routing == RoutingOff` — so with routing off, or on a base that had not yet shown it carries a preference, nothing was paced, struck or learned while every other controller went on acting. The ledger always records now; only what is EMITTED from it is configured, which was already gated at `providerPreferences` and `laneChoiceFor`. A base that is not a router gets a ledger with one row, not no ledger. `TestRoutingOffSendsNoPreferencesAndMeasuresNothing`, `TestRoutingOffTeachesTheBeliefNothing` and `TestRoutingOffNotesNothingForACut` are renamed and inverted; the manual's 'Only `off` stops both' is replaced."
  - "A `Tools:false` lane was never tried. `internal/lane/frontier.go` removed it from every tool-carrying request for good on a router flag this build had already measured wrong — the 2026-09-10 screenshot has GMICloud gated out of a request while it was serving that same task's tool calls six seconds at a time. `Tools`, `Uptime5m` and `Status` are priors now: a doubted lane is ranked behind every lane nothing is doubted about (`sheetDoubtsLast`), one request in ten probes it first, and a lane whose own answers have come back usable is not doubted at all — a belief that decays back toward the sheet's prior on `QualityHalfLife`. `frontier.go`'s `toolsLast` is `sheetDoubtsLast`. `Serves`, the wire's own negative, stays the one hard exclusion."
  - "A stream cut that named no server struck nothing, so `StreamCut.Rerouted` was false and the next attempt went back to the same lane deterministically — the one stall shape that could not reroute. It is now filed against the machine this request asked for (`provider.only` of one, else `provider.order[0]`, else a rescue's demand), which this process wrote itself. `Rerouted` is false only for a request that expressed no preference at all."
  - "A 429 was answered by waiting. The owner's ruling of 2026-09-10 — 'we need to handle not yet properly', nobody works a rate limit around by switching models themselves — is now the contract in code: the machine that said it comes off the next body and the next body goes out AT ONCE, with no backoff, because a backoff is what we pay to ask the SAME machine again. When every machine this request may use is held at once, a watched call hands the refusal straight back so `pacingExhausted` offers the next model (endpoints.go), and only a call nobody is watching waits — for the window the machine itself named, with that moment on `notePhase(PhasePaced…)` so a surface draws a real countdown instead of our doubling."
  - "`WithPatientRateLimits` meant 'sixty attempts against one machine'. It means 'may wait for the earliest window when there is nowhere else to go'; a patient call walks the machines exactly as a watched one does and reaches a wait by the same road. `patience.go`'s header says so."
  - "`provider.order` was treated as a way to steer a retry. It is a RANKING the router may ignore once `allow_fallbacks` is true; only `provider.ignore` takes a machine off the table, and that is what the next body now carries."
  - "`Client.refuseUpstream` returned a bool. It returns the `laneRefusal` it acted on, so the retry loop can read which machine must be off the next body without classifying the same refusal a second time."

Two new structural laws ride the `laws` gate: `TestNoLedgerWriteIsKeyedOnTheLaneWeChose` (`internal/provider/servedkey_law_test.go`) fails the build the day a ledger write takes a lane we merely chose — 3,728 of 10,107 finished attempts came back from a machine that was not the one chosen, and `lane: Fireworks` / `via DeepInfra` appears 104 times, so the wrong argument is both common and compiles. `TestRetryNeverRepeatsAMachine` runs 200 randomised scripted pools and fails on any identical (machine, body) pair sent twice while another machine was admissible.

Replicated end to end before the fix, in `internal/provider/neverrepeat_test.go`: a three-machine pool with two saturated answered in six sends to one machine and then failed; it answers in three now, one to each machine, with `2 of 6` on the status row and no status code anywhere a person can read. The tool-carrying screenshot (`TestATaskIsAnsweredByTheLaneTheSheetDoubts`) is answered by the machine the sheet flags `Tools:false`.
