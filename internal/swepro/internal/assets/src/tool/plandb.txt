PlanDB task graph coordination for all work.

Use this tool as the durable task state for every user request. The harness normally creates the root task before the model starts. Small tasks can stay as a one-node graph; larger tasks should be decomposed into agent work packages just in time as useful package boundaries become clear.

The PlanDB atomic unit is a work package, not an individual tool call. A package is one agent/subagent doing a linear tool loop internally. Normal `read`, `grep`, `edit`, `bash`, and test commands inside that package should be attributed to the active package, not turned into child PlanDB nodes.

Do not use bash to run PlanDB commands. This tool is the PlanDB interface. Use bash only for ordinary repo commands such as tests, builds, git status, or language tooling.

PlanDB is a compound task graph:
- tasks may contain subtasks recursively
- dependencies connect any tasks across the graph
- only ready leaf tasks should be scheduled for execution

Important scheduling rules:
- The orchestrator owns final integration, merge ordering, and root completion.
- Bounded orientation with ordinary reads/searches may happen under the root before child packages exist.
- For non-trivial work, once orientation reveals file scope or executable work packages, create/update the graph before continuing into implementation design or mutation.
- When the request already names concrete files and acceptance criteria, a few reads/searches are enough orientation; create the graph before extended option analysis, shell commands, edits, tests, or delegation.
- Create child packages only for meaningful work boundaries: delegation, parallelism, isolation, retry, review, or handoff.
- Do not split one coherent same-file implementation into serial micro-packages. If one agent will do the linear edits in one checkout, keep it one implementation package and let the agent's normal tool loop handle the internal steps.
- Worker/subagent tasks should receive the claimed PlanDB task id and must report completion through PlanDB.
- Subagents may launch nested subagents. Nested packages should default under the caller's assigned PlanDB task, not always under the root.
- Do not schedule composite parent tasks for execution.
- File scope may start as "unknown until probe", but write tasks with unknown file scope must not be executed.
- Read-only tasks can usually share the working checkout.
- Write tasks require either disjoint file scopes in the same checkout or an isolated worktree.
- Mark `worktree: required` when isolation is needed; do not treat it as proof that a worktree already exists.
- Integration tasks should run after dependent write/test branches converge.
- Context is not a transcript. Store only durable facts that downstream tasks must recall.

Every executable work-package description should include these contract lines:
task_role: probe|research|architecture|implementation|review|qa|security|integration|release|custom:<name>
access: read|write|integration
parallel: safe|serial
worktree: none|required
file_scope: concrete paths/globs or "unknown until probe"
agent: suggested subagent type
context_inputs: parent,deps,file_scope,domain
outputs: findings|patch|decision|review_report|test_report|risk_report|handoff
acceptance: how completion is verified

`task_role` is intentionally open-ended. Add specialized roles when useful; the scheduler should rely mainly on access, parallel, worktree, file_scope, and dependencies for safety.

Use `context` only for durable project discoveries, constraints, decisions, blockers, and patterns. Do not store command transcripts or low-value notes.

Before claiming or delegating a downstream task, use `show`, `contexts`, or `search` to recall relevant context, especially context attached to upstream dependencies or matching the task's file_scope.

Context propagation rules:
- Root orientation can produce durable context, but ordinary read/search transcripts should stay out of PlanDB.
- A package prompt should receive the user/root goal, parent package summary, dependency results, file_scope, constraints, and relevant decisions.
- Nested child packages inherit the caller's assigned task as parent plus the relevant context for their scope.
- Completed package results should be compact handoffs; downstream agents should not need to inspect the full conversation that produced them.

Useful operations:
- The harness normally initializes the project and root task before the model starts. Do not call `init` again when the prompt includes a PlanDB project/root reminder.
- `init` creates the graph only when no harness-created PlanDB project exists.
- `add` creates one task; `add_many` creates several tasks without shelling out.
- Prefer the **id-keyed** `add_many` shape for any non-trivial plan: give every task an explicit `id` and reference other tasks by that id in `deps` (bare strings) and `parent`. Example: `tasks:[{"id":"t0","title":...},{"id":"t1","title":...,"deps":["t0"]}]`. Ids are local to the document; ingestion maps them to real PlanDB ids and returns the `idMap`. `deps` may also reference an already-existing PlanDB task id.
- Id-keyed `add_many` is transactional: the WHOLE document is validated first (unique ids, every dep/parent resolvable, no cycles, field limits), and if anything is wrong NOTHING is created and the result lists EVERY violation at once — fix them all and resend the whole document, do not retry one error at a time.
- Emit ONE large document for the whole decomposition. Make it WIDE: give independent tasks no deps on each other so they land in the ready-set together and run in parallel. Add a `deps` edge only for a genuine ordering constraint. Hundreds of tasks in one id-keyed `add_many` is expected and preferred over many small batches.
- Legacy shape (no `id`, `deps` as `{taskId,kind}` structs referencing `taskKey`/title, inferred QA/review deps) is still accepted and auto-detected, but the id-keyed shape is more reliable at scale.
- In `add_many`, avoid serial chains of tiny same-file implementation tasks. Prefer a single implementation package plus downstream QA/review unless each split has a real independent owner, isolation requirement, or retry boundary.
- `list_ready` returns ready leaf tasks and filters unsafe unknown-scope write tasks by default.
- `claim` claims a specific ready task; prefer this over unfiltered next-task selection.
- `done` completes a task; include a compact result and changed files for write tasks.
- `context`, `contexts`, and `search` manage durable recall for downstream work.
- `amend`, `insert`, `update`, and `split` adapt the graph just in time.
- `status`, `overview`, `project_dag`, `critical_path`, `bottlenecks`, `what_unlocks`, and `ahead` inspect scheduling state.
