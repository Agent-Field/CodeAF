Writes per-candidate finding files under `.review/lens/<lens>/candidates/`.
Each candidate gets its own file (so appended evidence doesn't get scrambled
between candidates). Used by Lens Investigator agents.

Finding IDs are auto-assigned in the form `F<prefix><3-digit-counter>` where
prefix is the lens's first 4 alphabetical chars. e.g. `Fauth001`, `Fconc014`,
`Finje003`. You CANNOT pick the ID yourself.

Two operations:

- `op: "add"` — create a new candidate. Returns the assigned finding ID.
    Required: `lens` (the investigator's lens),
              `title` (one-line description),
              `file` (path to the suspect code),
              `severity_guess` (critical|high|medium|low|info),
              `confidence_guess` (number 0..1),
              `one_line_why` (one sentence: what makes this suspicious).
    Optional: `line` (line number in `file`).
    Creates `.review/lens/<lens>/candidates/F<id>.md` with structured
    frontmatter (lens, file, line, severity, confidence) and the one-line
    why. The full evidence + hypothesis are appended separately via
    `evidence_append` — keeps each tool call small.

- `op: "evidence_append"` — append a labeled block to an existing candidate.
    Required: `finding_id`, `lens`, `label`, `content` (markdown).
    Use `label` like "Evidence", "Hypothesis for the Prover", "Why this might
    be a bug". Appends `### <label>\n\n<content>\n`. Call this 2-4 times per
    candidate to build up the full case.

Bias toward RECALL when calling `add` — over-fire candidates. The Prover
will adversarially verify each, so false positives are caught downstream.
